# Blog Writing Guide

이 문서는 GitHub Pages 블로그 글을 작성할 때 사용하는 기준입니다.

## 1. 블로그의 역할

이 블로그는 포트폴리오 전용 사이트가 아니다. 다음 네 가지 역할을 함께 수행한다.

1. 실무 지식 저장소
2. 이력서·포트폴리오 근거 자료
3. 학습 기록
4. 생활, 가족, 주택, 재무, 장기 의사결정 등 다시 확인할 가치가 있는 개인 기록

글을 남길지 여부는 **IT와 관련 있는가**로 판단하지 않는다.

남길 가치가 있는 글은 다음 중 하나 이상에 해당한다.

- 실제로 경험하거나 해결한 일
- 나중에 다시 사용할 수 있는 지식
- 중요한 판단과 그 판단의 근거
- 시간이 지난 뒤 되돌아볼 가치가 있는 생활 기록
- 가족, 주거, 재무, 학습, 경력처럼 장기적으로 이어지는 계획

반대로 삭제 또는 비공개 후보는 다음과 같다.

- Jekyll/테마 설치 시 자동으로 포함된 예제·데모 글
- 내용 없는 테스트·placeholder 글
- 같은 내용을 의미 없이 중복한 글
- 본인이 작성한 기록이라고 보기 어려운 템플릿 원문
- 공개하면 안 되는 개인정보·회사 기밀·인증정보가 포함된 글

**비IT 글이라는 이유만으로 삭제하지 않는다.**

## 2. 글의 두 축

### Work / Tech / Study

개발, 서버 운영, 데이터베이스, 보안, 프로젝트 관리, AI workflow, 경력과 학습 기록이다.

주로 다음 질문에 답하도록 작성한다.

- 어떤 문제가 있었는가?
- 왜 문제가 발생했는가?
- 어떤 근거로 판단했는가?
- 어떻게 해결하거나 학습했는가?
- 다시 같은 상황이 오면 무엇을 재사용할 수 있는가?

### Life / Notes

주택, 가족 생활, 재무, 생활 개선, 장기 계획과 개인적인 의사결정 기록이다.

주로 다음 질문에 답하도록 작성한다.

- 무엇을 고민했는가?
- 당시 조건과 제약은 무엇이었는가?
- 어떤 선택지를 비교했는가?
- 무엇을 결정했고 왜 그렇게 결정했는가?
- 언제 다시 확인해야 하는가?

Life / Notes는 기술 글보다 중요도가 낮은 영역이 아니다. 목적과 독자가 다르므로 **목록만 분리**한다.

## 3. 기술·업무 카테고리 작성 기준

기술·업무 글은 아래 7개 카테고리를 우선 사용한다.

| Category | 사용 기준 |
|---|---|
| `backend` | Java, Spring Boot, API, 인증/권한, 웹 애플리케이션 구조 |
| `database` | SQL, DB 설계, Oracle, PostgreSQL, Tibero, 데이터 모델링 |
| `infrastructure` | Linux, Nginx, Apache, Tomcat, Podman, 배포, 장애 대응 |
| `data-systemization` | 분석 결과를 DB, API, 화면, 운영 시스템으로 연결하는 작업 |
| `security-audit` | 보안, 접근통제, 로그관리, 내부통제, CISA, ISMS-P |
| `project-management` | PMP, 요구사항 정리, 업무일지, 보고, 고객 커뮤니케이션 |
| `career` | 이직, 포트폴리오, 기술 블로그 운영, AI workflow, 경력 방향 |

기존의 `study` 카테고리 글은 과거 기록으로 유지할 수 있다. 새 글은 내용에 맞는 표준 카테고리로 작성한다.

개인 생활 기록은 `Personal` 태그를 사용하여 `/notes/` 목록으로 분리한다.

자세한 기준은 `docs/category-guide.md`를 따른다.

## 4. 기술 문제 해결 글 구조

```markdown
## 문제점

## 원인

## 해결

## 실행 방법

## 검증 방법

## 재발 방지 / 개선 방향
```

필요한 경우 마지막에 `포트폴리오 관점의 의미`를 추가할 수 있지만 모든 글에 강제하지 않는다.

## 5. 학습/개념 정리 구조

```markdown
## 배경

## 핵심 개념

## 실무 적용 기준

## 예시

## 주의점

## 정리
```

## 6. 생활·의사결정 글 구조

```markdown
## 배경

## 현재 조건

## 선택지

## 판단 근거

## 현재 결정

## 다시 확인할 시점
```

모든 항목을 항상 사용할 필요는 없지만, 나중에 다시 읽었을 때 당시 판단을 복원할 수 있어야 한다.

## 7. 프로젝트 경험 일반화 기준

업무 경험을 공개 글로 바꿀 때는 반드시 일반화한다.

| 원본 업무 기록 | 공개 글 표현 |
|---|---|
| 특정 고객사 서버 장애 | 공공기관 Linux 서버 장애 대응 |
| 내부 IP와 계정 포함 작업 | Linux 서버 접근 및 점검 절차 |
| 고객 회의록 | 요구사항 정리 과정에서 확인한 일반적 이슈 |
| 특정 DB명/스키마/테이블명 | 운영 DB 또는 분석 DB |
| 고객사 사업명 | 데이터 분석 시스템화 프로젝트 |

## 8. 제목 작성 기준

기술 글은 기술과 문제를 함께 드러낸다.

좋은 예:

- Rocky Linux 디스크 마운트 실패 대응 절차
- Apache VirtualHost 404 장애 원인 분석
- Podman으로 CloudBeaver를 운영할 때 고려할 점

생활 글은 무엇을 결정하거나 기록하는지 드러낸다.

좋은 예:

- 2030년까지 서울 내 집 마련을 어떻게 시도할 것인가
- 아이들과 집에서 시간을 보내기 위해 선택한 놀이 기준
- 생활비를 줄이기 위해 실제로 바꾼 소비 습관

내용을 알 수 없는 `오늘 한 일`, `생각`, `정리` 같은 제목은 피한다.

## 9. 민감정보 제거 체크리스트

공개 전 반드시 확인한다.

- [ ] 고객사명 제거 또는 일반화
- [ ] 내부 IP 제거
- [ ] 계정명 제거
- [ ] 비밀번호/토큰/키 제거
- [ ] 내부 경로 제거 또는 일반화
- [ ] 회의록 원문 제거
- [ ] 계약상 비공개 내용 제거
- [ ] 개인정보 최소화
- [ ] 가족의 불필요한 상세 개인정보 제거
- [ ] 정확한 자산·계좌·주소 등 공개할 필요 없는 상세값 제거
- [ ] 보안상 악용 가능한 상세값 제거

## 10. 이력서 / 포트폴리오 연결 기준

기술·업무 글 중 연결 가능한 글은 이력서 한 줄을 보완하는 근거로 활용한다.

모든 글이 이력서와 연결될 필요는 없다. 생활 기록과 개인 의사결정 글은 그 자체로 기록 가치가 있으면 유지한다.

## 11. 글 품질 기준

### 기술·업무·학습 글

- 제목만 봐도 주제가 보인다.
- 경험 또는 근거가 있다.
- 문제 해결이나 학습 과정이 재사용 가능하게 정리되어 있다.
- 민감정보가 제거되어 있다.

### 생활·개인 기록

- 당시 상황과 판단 근거가 남아 있다.
- 단순한 일회성 메모보다 나중에 다시 볼 이유가 있다.
- 필요한 경우 다시 확인할 시점이나 조건이 명시되어 있다.
- 공개할 필요 없는 개인정보는 제거되어 있다.

## 12. 검색 노출(SEO) 기준

검색엔진을 위한 별도 글을 쓰지 않고, 사람이 검색하거나 다시 찾을 만한 내용을 정확한 제목과 설명으로 표현한다.

새 글에는 가능하면 `description`을 명시한다.

```yaml
---
layout: post
title: "Nginx 리버스 프록시에서 Tomcat 404를 진단한 방법"
description: "Nginx와 Tomcat 사이의 프록시 경로 불일치로 발생한 404를 로그와 설정 비교로 진단하고 재발 방지 기준을 정리합니다."
date: YYYY-MM-DD
categories: [infrastructure]
tags: [Nginx, Tomcat, Troubleshooting]
---
```

생활 글도 같은 원칙을 적용한다.

```yaml
---
layout: post
title: "2030년까지 서울 내 집 마련을 어떻게 시도할 것인가"
description: "공공분양과 송파·올림픽공원 생활권 구축주택을 단계적으로 검토하는 장기 주거 의사결정 기록입니다."
date: YYYY-MM-DD
categories: [career]
tags: [Personal, Housing, Decision Log]
---
```

### 제목과 본문

- 실제 검색하거나 다시 찾을 표현을 제목에 쓴다.
- 첫 문단에서 글의 목적을 명확히 한다.
- H2/H3만 읽어도 흐름이 보이게 한다.
- 관련 기존 글이 있으면 내부 링크를 추가한다.
- 외부 사실을 설명할 때는 가능하면 공식 출처를 우선한다.
- 이미지는 의미 있는 파일명과 `alt` 설명을 사용한다.
- 키워드 스터핑은 하지 않는다.

### 게시 후

사이트는 `jekyll-seo-tag`, `jekyll-sitemap`, `robots.txt`를 사용한다. 새 글마다 별도의 긴 SEO 작업을 반복하지 않는다.

중요한 신규 글이나 사이트 구조 변경 시 Google Search Console에서 URL 검사 또는 사이트맵 상태를 확인한다. 검색 노출보다 **나중에 다시 사용할 수 있는 실제 기록**을 우선한다.
